# 敵データのアセット化と敵スキル割り当て 設計書

- 日付：2026-11-22
- 対象：ステージ・敵データの持ち方（ScriptableObject）と、全30ステージへの敵スキル割り当て

## 1. 目的（なぜやるか）

現状、ほとんどの敵が2ステージ連続で登場するが、2戦目はHPが少し増えるだけで名前・顔・戦い方が同じ。プレイヤーからは「同じステージをもう一度遊ばされている」ように見えて単調。

そこで次の2つを同時に行う。

1. 敵ごとに「得意技」を持たせ、2戦目は「本気モード」（得意技のLvが1上がり、技が1つ増える）にして、再戦に意味を持たせる
2. 敵を独立したアセット（ScriptableObject）にし、「敵の個性」と「2戦目は1段階強い」というルールをデータの形そのもので表現する

あわせて、敵スキル10種（実装済み・未使用）を初めて実際のステージに登場させる。

## 2. ゴール / 非ゴール / アンチゴール

### ゴール
- 敵1体＝1アセット。名前・顔画像・得意技・2戦目の追加技を持つ
- ステージは「どの敵か」「2戦目か」を持ち、技はルールから自動で決まる
- 既存の実データ（`Assets/Resources/StageConfigList.asset` の30ステージ）を失わずに移行する
- 全30ステージに敵スキルが割り当てられた状態にする（§6の表）
- ステージ詳細画面・HUD・ステージ選択・クリア/ゲームオーバー画面が従来どおり敵名・顔・Lv・技を表示する
- 盤面用スプライトが未設定でも、炎マス・時限爆弾・岩がプレイヤーに見える（仮の色付け、§6.7）

### 非ゴール
- 顔画像の新規作成（足りない敵は顔なしのまま。別作業）
- 炎マス・爆弾ぷよ・岩の盤面用スプライト（画像素材）の作成（別作業。今回はコードによる仮の色付けで代用）
- 各スキルの数値（`EnemySkillBalanceConfig`）の本格調整。実プレイ後に行う
- ステージ数・並び順・HP・制限時間など盤面パラメータの再設計（ステージ1のHPのみ例外、§7）
- 敵ごとに強化の形を変える仕組み（全員同じルール。物足りない敵は後で個別調整）

### アンチゴール（動いても失敗とみなすもの）
- 移行で既存30ステージの敵名・画像・HP・盤面設定が1つでも失われる／ずれる
- ステージ側が敵を番号で参照する（並べ替えで別の敵を指す壊れやすい形）
- 実データを仮データで上書きできる危険なエディタメニューが残る
- 1ステージで同時に発動する技が多すぎてプレイヤーが対処を考える前に破綻する（上限：前半は2つ、後半17〜30は3つ）

## 3. 制約

- Unity 6 系、C# `#nullable enable`、既存のコーディング規約（日本語コメント、ViewBase 継承など）に従う
- `StageConfigList` は `Resources.Load` によるシングルトン（`StageConfigList.Instance`）。読み込み方式は変えない
- `StageConfig` を読んでいる箇所：`EnemyController`（Name/Sprite/Hp）、`GameMainController`（EnemySkills/EnemyLevel/盤面設定）、`StageDetailView`、`StageSelectView`。`GameClearState`/`GameOverState` は `EnemyController` 経由
- **シリアライズ済みフィールドを消すとアセットの値が失われる**。移行は「新旧フィールド共存 → 移行実行 → 旧フィールド削除」の順で行う必要がある
- ステージデータは今後 Inspector で直接編集する方針（`StageConfigPopulatorEditor` 冒頭コメントより）
- Unity エディタはユーザーが開いており、Claude が操作してよい（移行メニューの実行・目視確認）

## 4. 検討した案

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A（採用）** | 敵を1体1アセット（`EnemyData`）にし、ステージはアセット参照＋「2戦目フラグ」を持つ | 名前・顔の重複が消える。得意技を直せば両ステージに反映。参照はドラッグ＆ドロップで並べ替えに強い | 30ステージの移行が必要。読み込み箇所の修正 |
| B | 敵一覧を1アセット（配列）にし、ステージは番号で参照 | 全敵を1画面で見渡せる | 番号参照は並べ替えで壊れる。6月に削除した `EnemyStatusList` の形に戻る |
| C | 構造はそのまま、各ステージに技を直接書く | 変更最小 | 重複が残る。2戦目ルールを表現できず、一括書き込みツール（上書きの危険）に頼る |

ユーザーが A を選択。「敵ごとの個性」と「2戦目は1段階強い」という狙いを、データの形が直接表すため。

## 5. ユーザーが決めたこと

- 同じ敵の2戦目は「本気モード」で強化する（案A：素材追加なし）
- 強化は全員同じルール：**2戦目＝得意技のLv+1、技を1つ追加**
- ステージ1・2・3は技なし
- 同時発動の技の上限とバランス、敵ごとの得意技の割り当ては Claude に任せる
- 敵スキルは組み合わせてよい。強い敵は1戦目から複数の技を使う
- データ構造は案A
- 盤面用の画像がない技（炎・時限爆弾・岩）は、今回コードによる仮の色付けで見えるようにする

## 6. 設計

### 6.1 `EnemyData`（新規 ScriptableObject）

`Assets/Scripts/App/GameMain/EnemyData.cs`。`[CreateAssetMenu(menuName = "WrestlePachi/EnemyData")]`。

| フィールド | 型 | 意味 |
|---|---|---|
| `DisplayName` | `string` | 表示名（例：クロマスク） |
| `FaceSprite` | `Sprite?` | 顔画像。未作成の敵は null |
| `SignatureSkills` | `EnemySkillEntry[]` | 1戦目（または1回だけ出るボス）の技とLv。空なら技なし |
| `RematchExtraSkills` | `EnemySkillEntry[]` | 2戦目で追加される技とLv。空なら追加なし |

- アセットは `Assets/Settings/Enemies/` に置く（`Resources` 配下にはしない。`StageConfigList` から直接参照されるため）
- ファイル名は英数字（例：`Enemy_KuroMask.asset`）。命名の細部は実装者判断
- `EnemySkillEntry` の既存 `PropertyDrawer`（`EnemySkillEntryDrawer`）がそのまま効くので、Inspector は「[Type▾] Lv[__]」の1行表示になる

### 6.2 技の決定ルール（純粋関数）

`EnemySkillRule.Resolve(EnemyData? enemy, bool isRematch) : EnemySkillEntry[]`（静的クラス。テスト可能にするため Unity 依存を持たせない）

- `enemy == null` → 空
- 1戦目（`isRematch == false`）→ `SignatureSkills` をそのまま（コピー）
- 2戦目 → `SignatureSkills` の各Lvを +1（上限 `MaxSkillLevel = 3`）＋ `RematchExtraSkills`
- 同じ Type が重複した場合は Lv の高い方を残す（防御的処理。§6.4 の表では発生しない）

### 6.3 `StageConfig` の変更

最終形：

| 種別 | 名前 | 内容 |
|---|---|---|
| 新フィールド | `EnemyData? Enemy` | どの敵か |
| 新フィールド | `bool IsRematch` | 同じ敵の2戦目か |
| 残すフィールド | `EnemyHp` ほか盤面・ゲームパラメータ全部 | 変更なし |
| 削除するフィールド | `EnemyName` / `EnemySprite` / `EnemyLevel` / `EnemySkills` | 移行後に削除 |
| 読み取り専用プロパティ | `EnemyName` | `Enemy?.DisplayName ?? ""` |
| 読み取り専用プロパティ | `EnemySprite` | `Enemy?.FaceSprite` |
| 読み取り専用プロパティ | `EnemyLevel` | `IsRematch ? 2 : 1`（HUD・詳細画面の「Lv.N」表示用） |
| 読み取り専用プロパティ | `EnemySkills` | `EnemySkillRule.Resolve(Enemy, IsRematch)` |

旧フィールドと同名のプロパティを用意するので、`EnemyController`・`GameMainController`・`StageDetailView`・`StageSelectView` の呼び出し側は原則無変更で済む。

`EnemyLevel` を「2戦目なら2」と自動にするのは Claude の判断（もともと「同じ敵を使い回すときの差別化用、表示のみ」という用途だったため、2戦目フラグと一致する）。

### 6.4 敵と技の割り当て（Claude の判断、ユーザー委任済み）

方針：
- 新しい技は、まず1戦目の得意技として単独で登場させ、覚えてもらってから組み合わせる
- 顔や名前から連想できる技を得意技にする
- 強い敵ほど複数の技を組み合わせて使う（ユーザー指示）。段階は次のとおり。Lv上限3、同時発動は最大3つ

### 6.6 移行手順

1. **共存フェーズ**：`StageConfig` に新フィールド（`Enemy`, `IsRematch`）を追加する。旧フィールドは C# 上で同名プロパティと並べられないため、`LegacyEnemyName` などに改名して `[FormerlySerializedAs("EnemyName")]` を付け、`[HideInInspector]` で残す（アセットの値は改名後のフィールドに読み込まれる）。この段階では読み取りプロパティは新フィールドを優先し、`Enemy` 未設定なら旧フィールドにフォールバックする（移行途中でもゲームが動く）
2. **移行メニュー**（エディタ専用、1回限り）：`WrestlePachi/敵データ移行（1回限り）`
   - 旧 `EnemyName` ごとに `EnemyData` アセットを作成（既に同名アセットがあれば再利用＝冪等）
   - 旧 `EnemySprite` を `FaceSprite` に引き継ぎ、§6.5 の新規3体に顔を設定
   - §6.4 の表に従って `SignatureSkills` / `RematchExtraSkills` を設定
   - 各ステージの `Enemy` を設定し、直前ステージと同じ敵なら `IsRematch = true`
   - ステージ1の `EnemyHp` を 2500 → 20 に修正（§7）
   - 実行前に確認ダイアログを出し、実行後に結果（作成した敵数・ステージごとの敵/2戦目/技）をログ出力
3. **確認**：Claude が Unity でメニューを実行し、ログ・Inspector・ステージ詳細画面で30ステージを確認
4. **後片付けフェーズ**：旧フィールド・フォールバック・移行メニューを削除し、`StageConfigList.asset` を再シリアライズして旧キーを消す（`AssetDatabase.ForceReserializeAssets`）
5. `StageConfigPopulatorEditor.cs`（古い25ステージの仮データで実データを上書きするメニュー）を削除
6. `EnemySkillType.cs` などのコメントで「StageConfig.EnemySkills に設定」と書かれている箇所を「EnemyData に設定」へ更新

### 6.7 盤面に見た目のない技の仮表示（ユーザー決定：仮の色付けで対応）

`EnemySkillAssets` の `_fireTileSprite` / `_bombPuyoSprite` / `_rockHitSprite` はすべて未設定。現状のコードでは次のとおり「見えない罠」になる。

- 炎：`PuyoBoard.AddFireTile` は sprite が null だとマーカーを作らない → 炎マスが見えない
- 時限爆弾：`PuyoBoard.PlaceBomb` が null の sprite で `PuyoPiece.Setup(OJAMA, …)` する → 爆弾ぷよが見えない
- 岩：`ConvertToRock` で見た目が変わらない → 1回で消えない理由がわからない

スプライトが設定されていればそれを使い、未設定のときだけ次の仮表示にする（画像が後から入れば自動でそちらが優先される）。

| 対象 | 仮表示 |
|---|---|
| 炎マス | マスの背後に半透明のオレンジ（目安 `#FF7A1A`、α0.45前後）の四角を表示。四角のスプライトは実行時に生成してよい |
| 時限爆弾 | 通常のお邪魔ぷよのスプライトを使い、赤（目安 `#FF4040`）に染める |
| 岩 | 岩化した時点で元のぷよを灰色（目安 `#8C8C8C`）に染める。ヒット後スプライトが未設定なら、ヒット時はさらに暗い灰色にする |

- 色の目安値は実装者が実機で見やすく調整してよい
- `PuyoPiece` の点滅などの演出が `_renderer.color` を一時的に変えて戻す処理と衝突しないこと（演出後に仮の色へ戻ること）

### 6.8 確認方法

- `EnemySkillRule.Resolve` は純粋関数なので、EditMode テストで「1戦目そのまま」「2戦目 Lv+1・上限3・追加技」「enemy null」「Signature 空で2戦目は追加技のみ」を検証する（テスト用アセンブリの置き方は計画で決める。`com.unity.test-framework` 1.6.0 は導入済み、テストアセンブリは未作成）
- 移行後、`StageConfigList.asset` の30ステージについて、移行前の敵名・画像・HP・盤面パラメータと一致すること（ステージ1のHPのみ意図的に変更）をスクリプトで照合
- Unity 上でステージ詳細画面を数ステージ開き、敵名・顔・Lv・技一覧が表示されること
- 技ありのステージ（例：5・8・10・17）を実際にプレイして技が発動し、炎マス・爆弾・岩が仮の色で見えること

## 7. Claude の判断事項（設計承認をもって確定）

- ステージ1の HP 2500 はテスト値の残りと判断し、20 に戻す（ステージ2が30のため、その手前の値）
- `EnemyLevel` は「2戦目なら2、それ以外は1」と自動化（Inspector での手入力をやめる）
- 顔の新規割り当て3体（グリム＝ドクロ、バジリスク王＝緑の怪獣、ブラッディゴリラ＝ゴリラ）
- `EnemyData` は `Assets/Settings/Enemies/` に配置
- §6.4 の割り当て表全体
- §6.7 の仮表示の色

## 8. 前提となる作業順

- 作業ツリーにある StageDetailView の未コミット変更（Lv表示 `_enemyLevelText` など）は、本件とは別の変更として先にコミットしておく。本件の表示確認で、どちらの変更が原因かを切り分けられるようにするため
